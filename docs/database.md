# Database

PostgreSQL, accessed with Drizzle ORM. Schema: `src/lib/db/schema.ts`. Migrations: `drizzle/` (plain SQL, generated by `drizzle-kit`, applied by `scripts/migrate.ts`).

## Tables

| Table                | Purpose                               | Notes                                                                                                                                                                                                                     |
| -------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `places`             | A journal entry pinned on the map     | `slug` unique; `status` draft/published; `published_at` (future = scheduled); `deleted_at` (soft delete); `location_privacy` exact/approximate; geocoder provenance (`geocoder_provider`, `provider_place_id`); `is_demo` |
| `photos`             | Metadata for photos in object storage | `storage_key` (base key; variants derived); `place_id` NULL = in the media library; `blur_data_url`                                                                                                                       |
| `trips`              | Multi-stop journeys                   | Group the timeline and draw dashed routes                                                                                                                                                                                 |
| `tags`, `place_tags` | Free-form tags                        | Many-to-many                                                                                                                                                                                                              |
| `bucket_list_items`  | Planned destinations                  | `linked_place_id` only counts as a visit when the place is published                                                                                                                                                      |
| `site_settings`      | One-off flags                         | e.g. "demo content was seeded once"                                                                                                                                                                                       |

Travel routes are _derived_ from a trip's dated places (great-circle arcs), so there is no `travel_routes` table.

## Conventions and why

- **UUID primary keys** (spec). The tables are small, so random-UUID index locality is a non-issue.
- **`timestamptz` everywhere**, defaults from the database (`now()`); `updated_at` is maintained by a trigger (`0001_security_and_triggers.sql`), never by the client.
- **Every foreign key is indexed**; hot read paths use a partial index (`places_public_idx … WHERE status = 'published' AND deleted_at IS NULL`).
- **Integrity in the database**, not just the app: slug format, coordinate ranges, rating 1–5, country code `[A-Z]{2}`, "a published place must have a `published_at`", trip dates ordered.
- **Row Level Security is enabled on every table with no policies.** The server connects with a privileged role (which bypasses RLS). On hosts that expose an auto-generated Data API (Supabase PostgREST), the anonymous/authenticated roles therefore cannot read or write anything. All public reads go through the server, which applies the "published and live" rule and the privacy rounding.
- **Soft delete** for places; photos removed from a place return to the media library; deleting a trip leaves its places.

## Visibility rule (single definition)

A place is public when `status = 'published' AND deleted_at IS NULL AND published_at <= now()` (and, when demo content is off, `is_demo = false`). This lives in one function (`publiclyVisible` in `places.repository.ts`) and is covered by integration tests.

## Commands

```bash
npm run db:generate        # after editing schema.ts → creates drizzle/NNNN_*.sql (review it!)
npm run db:migrate         # applies pending migrations to DATABASE_URL
npm run db:seed            # inserts DEMO content (flagged is_demo) once; --force to repeat
npm run db:purge-demo      # deletes every is_demo row (real content untouched)
```

In development without `DATABASE_URL` the embedded database applies migrations automatically on boot.

## Upgrading to PostGIS (when you need nearest-neighbour or bounding-box SQL)

1. `CREATE EXTENSION postgis;` (Neon, Supabase, RDS and most managed hosts support it).
2. Add a generated column and index — no data migration needed:
   ```sql
   ALTER TABLE places
     ADD COLUMN geog geography(Point, 4326)
     GENERATED ALWAYS AS (ST_SetSRID(ST_MakePoint(lng::float8, lat::float8), 4326)::geography) STORED;
   CREATE INDEX places_geog_gix ON places USING gist (geog);
   ```
3. Replace `findNearbyPlaces` (currently a haversine scan in `features/places/nearby.ts`) with `ST_DWithin` / `ORDER BY geog <-> …`.

Do this only if the number of public places grows into the thousands; today a scan of a few hundred rows is faster than a round trip.

## Backups and restores

Treat backups as a feature you have _tested_:

1. Enable automated daily backups with point-in-time recovery at your provider (Neon, Supabase and RDS all offer it).
2. Photos live in object storage, not the database: enable **bucket versioning** (or a scheduled copy to a second bucket) so a deleted photo can be recovered.
3. Once a quarter, restore the latest backup into a scratch database, point a local `DATABASE_URL` at it, run `npm run dev` and open a few places. A backup you have never restored is a hope, not a backup.
4. Before risky migrations: take a manual snapshot first.
